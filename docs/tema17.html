Depuración, pruebas y mejora de programas

Cómo pasar de «algo falla» a una causa concreta, comprobar la corrección y dejar un programa más claro, robusto y fácil de mantener.

Programar no consiste solo en conseguir una salida correcta una vez. También exige comprender los fallos, anticipar entradas difíciles, comprobar funciones y mejorar el código sin alterar por accidente su comportamiento. Este recorrido desarrolla la elaboración, depuración y prueba de programas prevista en el currículo.[90]

Antes de empezar: un programa que supera tres ejemplos puede seguir siendo incorrecto. La pregunta útil no es únicamente «¿funciona?», sino «¿en qué condiciones funciona, cómo lo sé y qué ocurrirá cuando cambie?».
Al terminar serás capaz de…
  • distinguir errores de sintaxis, excepciones y errores lógicos;
  • leer un mensaje de error y seguir una traza hasta el punto relevante;
  • reproducir un fallo e inspeccionar la ejecución paso a paso en Thonny;
  • gestionar errores previsibles con try, except, else y finally;
  • diseñar casos normales, casos límite y entradas no válidas;
  • comprobar funciones mediante resultados esperados y aserciones;
  • refactorizar y volver a ejecutar las pruebas para detectar regresiones;
  • documentar y dar estilo al código pensando en su mantenimiento.

1. Errores de sintaxis, excepciones y errores lógicos

Un fallo es el comportamiento observable que no coincide con lo esperado; su causa es la condición del código o de los datos que lo provoca. Cambiar líneas al azar puede hacer desaparecer el síntoma, pero depurar significa formular una explicación y comprobarla.

Tres familias de problemas que requieren respuestas diferentes
TipoQué sucedeEjemploPrimera pista
Error de sintaxisEl código no respeta la gramática de Python y no puede empezar a ejecutarse.Falta : tras un if o queda un paréntesis abierto.SyntaxError, línea señalada y posición aproximada.
ExcepciónLa sintaxis es válida, pero durante la ejecución ocurre una operación que no puede completarse.Convertir "dos" con int() o dividir entre cero.Tipo, mensaje y traza de la excepción.
Error lógicoEl programa termina, pero calcula o decide algo incorrecto.Usar > cuando el límite también debería admitirse con >=.Una prueba falla o el resultado contradice el esperado.

La documentación de Python distingue expresamente los errores de sintaxis de las excepciones detectadas durante la ejecución.[91] Los errores lógicos son más silenciosos: como el intérprete puede ejecutar el programa, hay que descubrirlos comparando el resultado real con un resultado previsto.

def precio_con_descuento(precio, porcentaje):
    # Falla lógicamente: suma el descuento en vez de restarlo.
    return precio + precio * porcentaje / 100

print(precio_con_descuento(80, 25))  # 100.0; se esperaba 60.0
Analogía: médico, no adivinoEl síntoma «sale 100» no identifica la causa. Como en un diagnóstico, se reúnen indicios, se propone una hipótesis —«el signo es incorrecto»—, se modifica una causa concreta y se repite la comprobación.

2. Lectura de mensajes de error y trazas de ejecución

Cuando una excepción no se gestiona, Python muestra un traceback o traza de pila. La última línea suele indicar el tipo de excepción y su mensaje; las líneas anteriores muestran la cadena de llamadas que llevó hasta ella. La documentación oficial señala que el nombre de la excepción aparece en el mensaje y que la traza aporta el contexto de ejecución.[91]

Traceback (most recent call last):
  File "notas.py", line 8, in <module>
    print(media([]))
  File "notas.py", line 5, in media
    return sum(valores) / len(valores)
ZeroDivisionError: division by zero
1 — Leer el final

ZeroDivisionError clasifica el problema y division by zero lo concreta. No es todavía una explicación completa de por qué la lista quedó vacía.

2 — Localizar el último marco propio

La línea 5 de media intentó dividir entre len(valores). Si la traza incluyera código de bibliotecas, convendría buscar primero el marco perteneciente al programa.

3 — Subir por las llamadas

La línea 8 llamó a media([]). La traza se lee como un itinerario: cada marco indica archivo, línea y función.

4 — Formular una hipótesis

La función no define qué debe hacer con una colección vacía. Hay que decidir su contrato: rechazarla claramente o asignarle un resultado con significado, no esconder la división.

Una flecha o una línea señalada indica dónde se detectó el error, que no siempre coincide con el lugar donde nació la causa. Un paréntesis abierto en una línea anterior puede producir un aviso más tarde; un dato incorrecto puede recorrer varias funciones antes de causar una excepción.

No borres la evidencia demasiado prontoAntes de editar, conserva el mensaje completo, la entrada usada y los pasos que reproducen el fallo. «Ha dado error» pierde la información necesaria para investigar; copiar solo la última línea puede ocultar cómo se llegó hasta ella.

3. Depuración paso a paso con Thonny

En este tema, Thonny se usa de forma puntual como segundo entorno: permite repetir un fallo en un programa .py, detener la ejecución, ver variables y avanzar instrucción a instrucción. Su sitio oficial presenta una vista de variables y un depurador que sigue la estructura del programa y permite observar la evaluación de expresiones.[94]

def contar_aprobados(notas):
    total = 0
    for nota in notas:
        if nota > 5:       # Sospecha: ¿qué ocurre con 5?
            total += 1
    return total

print(contar_aprobados([4, 5, 7]))  # Se espera 2, devuelve 1
Reproducir

Ejecutar el mismo archivo con la entrada mínima [4, 5, 7] y confirmar que devuelve 1. Si no se reproduce, todavía no se está investigando el mismo fallo.

Detener

Colocar un punto de interrupción en el if para evitar recorrer a mano todo el programa. Thonny permite añadir puntos de interrupción desde el margen de números de línea.[95]

Inspeccionar

Observar nota y total en cada vuelta. Cuando nota vale 5, la condición es falsa y el contador no cambia.

Avanzar paso a paso

Entrar en la función cuando interese su interior, avanzar sobre una llamada cuando no sea relevante y continuar hasta el siguiente punto. El objetivo es relacionar cada instrucción con el cambio de estado.

Corregir y repetir

Cambiar > por >=, ejecutar de nuevo el caso que fallaba y después el conjunto completo de pruebas.

Depurar no es mirar una animación completa. Detén el programa cerca del lugar donde el estado pasa de correcto a incorrecto. Compara el valor que ves con el que debería existir en ese instante; esa diferencia convierte la observación en evidencia.

4. Gestión de excepciones con try, except, else y finally

Algunos problemas son previsibles: una persona puede escribir texto donde se espera un entero o un archivo puede no estar disponible. Gestionar una excepción permite responder de forma controlada. No significa envolver todo el programa para que «nunca falle», sino capturar solo aquello que se sabe interpretar.

def leer_edad(texto):
    try:
        edad = int(texto)
    except ValueError:
        return "La edad debe ser un número entero."
    else:
        if edad < 0:
            return "La edad no puede ser negativa."
        return edad
    finally:
        print("Entrada revisada")
Responsabilidad de cada parte
CláusulaCuándo se ejecutaUso adecuado en el ejemplo
trySiempre, hasta completarse o producir una excepción.Contiene la conversión que puede lanzar ValueError.
except ValueErrorSolo si aparece ese tipo compatible de excepción.Traduce el fallo previsto a un mensaje útil.
elseSi el bloque try termina sin excepción.Trabaja con el entero ya convertido y valida su significado.
finallyAl abandonar la estructura, haya o no excepción.Realiza una acción que debe ocurrir siempre; en casos reales suele reservarse para limpieza necesaria.

Conviene capturar tipos concretos. Python organiza las excepciones incorporadas en una jerarquía, de modo que una cláusula que menciona una clase también alcanza sus subclases.[92] Un except Exception: demasiado amplio puede ocultar un defecto inesperado —por ejemplo, un nombre mal escrito— como si fuese una entrada corriente.

Excepción

Indica que una operación no pudo completarse, como convertir "dos" a entero. Se gestiona si el programa sabe responder de forma útil.

Validación

Comprueba si un valor ya obtenido cumple las reglas del problema, como que una edad sea no negativa. No todas las entradas no válidas necesitan provocar una excepción.

Silenciar no es solucionarUn bloque except: pass descarta el tipo, el mensaje y la traza. El programa puede continuar con datos incompletos y fallar después, lejos de la causa original.

5. Casos normales, casos límite y entradas no válidas

Una prueba comienza antes de ejecutar código: hay que elegir una entrada y escribir el resultado esperado. Los casos se seleccionan por lo que representan, no para acumular ejemplos parecidos.

Diseño de casos para una función es_nota_valida(nota) que admite valores entre 0 y 10, ambos incluidos
FamiliaEntradaResultado esperadoQué comprueba
Normal7TrueUn valor claramente situado dentro del intervalo.
Límite inferior0TrueQue el extremo inferior está incluido.
Límite superior10TrueQue el extremo superior está incluido.
Junto al límite-0.1 y 10.1False y FalseQue no se aceptan valores apenas exteriores.
No válida por tipo"notable"Rechazo definido por el contratoQue la función no interpreta texto arbitrario como nota.

Un caso normal representa el uso habitual. Un caso límite se sitúa en un borde o cerca de él: cero elementos, primer o último índice, mínimo o máximo permitido. Una entrada no válida incumple el tipo, el formato o las reglas del problema. También conviene distinguir una entrada válida pero excepcional —por ejemplo, una lista con un único elemento— de una entrada que el contrato prohíbe.

Analogía: probar un puenteNo basta con cruzarlo una vez con un coche medio. Se comprueba la carga habitual, las condiciones cercanas al límite y lo que debe rechazarse. Las pruebas útiles exploran fronteras donde suelen cambiar las decisiones del programa.

La especificación decide el resultado

Para una lista vacía, una media podría rechazarse con ValueError, devolver None o adoptar otra regla acordada. Ninguna opción es correcta por sí sola: debe estar definida, documentada y probada. Sin un resultado esperado, ejecutar un caso produce una observación, pero no una prueba concluyente.

Pregunta de diseño: ¿qué valores hacen cambiar de rama a la condición? Si el código contiene 0 <= nota <= 10, los puntos 0 y 10 y sus vecinos son más informativos que probar cinco valores centrales.

6. Pruebas de funciones con resultados esperados y aserciones

Las funciones breves con entradas y retornos claros se pueden comprobar de forma aislada. Una prueba prepara datos, ejecuta la función y compara el resultado real con el esperado. La sentencia assert expresa esa condición: si es falsa, lanza AssertionError; puede incluir un mensaje que explique la expectativa.[93]

def es_nota_valida(nota):
    return (isinstance(nota, (int, float))
            and not isinstance(nota, bool)
            and 0 <= nota <= 10)

assert es_nota_valida(7) is True
assert es_nota_valida(0) is True
assert es_nota_valida(10) is True
assert es_nota_valida(-0.1) is False
assert es_nota_valida(True) is False
assert es_nota_valida("notable") is False

La exclusión explícita de bool evita aceptar True como si fuera 1: en Python los booleanos son una subclase de los enteros. Si todas las aserciones se cumplen, el programa no muestra nada. Ese silencio significa únicamente que esos casos concretos han pasado; no demuestra que la función sea correcta para cualquier entrada. Si una aserción falla, Python señala qué expectativa no se cumplió y se conserva el caso como protección frente a futuros cambios.

Preparar

Elegir entradas pequeñas y representativas. Cada caso debe tener una razón: uso normal, frontera, error observado o regla importante.

Ejecutar

Llamar directamente a la función. Separar cálculo de input() y print() evita tener que simular toda la conversación.

Comparar

Escribir el esperado antes de aceptar el resultado real. Si difieren, se investiga; no se cambia la expectativa solo para que la prueba pase.

Conservar

Mantener la prueba después de corregir el fallo. Así avisa si una modificación futura vuelve a introducirlo.

Las aserciones de prueba no sustituyen la validación de datos de una aplicación. La referencia de Python explica que assert depende de __debug__ y que su código puede omitirse al solicitar optimización.[93] Por eso no deben ser la única barrera para una entrada real ni usarse para errores que el programa necesita gestionar siempre.

Una prueba debe poder repetirse. Mismas entradas y mismo estado inicial deberían producir el mismo resultado esperado. Si depende de una respuesta manual o de mirar la pantalla, es más difícil repetirla tras cada cambio.

7. Refactorización, eliminación de duplicación y nueva ejecución de las pruebas

Refactorizar es cambiar la estructura interna del código sin cambiar su comportamiento observable. Se hace para reducir duplicación, aclarar nombres, acortar funciones o separar responsabilidades. Corregir una fórmula y añadir una función nueva cambian el comportamiento; pueden ser mejoras necesarias, pero no son por sí solas refactorización.

Antes: regla duplicada

if nota1 >= 5:
    print("Aprobada")
else:
    print("No aprobada")

if nota2 >= 5:
    print("Aprobada")
else:
    print("No aprobada")

Después: una sola decisión

def resultado(nota):
    if nota >= 5:
        return "Aprobada"
    return "No aprobada"

print(resultado(nota1))
print(resultado(nota2))

La segunda versión concentra la regla en una función y evita que dos copias evolucionen de forma distinta. Sin embargo, que parezca más limpia no garantiza que conserve el comportamiento: antes de cambiar se necesitan pruebas que describan el contrato.

1 — Establecer una base

Ejecutar las pruebas y comprobar que pasan. Si alguna ya falla, hay que registrarlo para no atribuir el problema a la refactorización.

2 — Hacer un cambio pequeño

Extraer una regla duplicada, renombrar una variable o dividir una función. Cambios pequeños permiten localizar con rapidez qué modificación introdujo una diferencia.

3 — Repetir todas las pruebas

No solo la prueba cercana al cambio: otra función puede depender del comportamiento modificado. Un fallo nuevo es una posible regresión.

4 — Continuar o deshacer

Si el comportamiento se conserva, se realiza el siguiente cambio. Si no, se investiga antes de acumular más modificaciones.

No mezcles objetivos innecesariamenteCorregir un fallo, cambiar resultados y reorganizar muchas partes a la vez hace difícil saber qué modificación tuvo cada efecto. Primero fija el comportamiento esperado; después mejora la estructura en pasos comprobables.

8. Documentación, estilo y mantenimiento del código

El código se mantiene cuando otra persona —o su autor semanas después— puede entender qué promete, modificar una parte y comprobar que el resto sigue funcionando. La claridad no se añade al final como decoración: reduce errores durante toda la vida del programa.

def calcular_media(notas):
    """Devuelve la media de una secuencia no vacía de notas."""
    if not notas:
        raise ValueError("Se necesita al menos una nota")
    return sum(notas) / len(notas)

PEP 8 reúne convenciones destinadas a mejorar la legibilidad y la coherencia del código Python; también recuerda que la coherencia dentro de un proyecto es especialmente importante.[96] Entre las pautas iniciales están usar cuatro espacios por nivel de sangría, separar visualmente partes y elegir nombres comprensibles. Una guía orienta: no justifica reescribir código estable solo para producir cambios cosméticos.

Analogía: un sendero mantenidoLos nombres son señales, las funciones delimitan tramos, la documentación explica el destino y las pruebas comprueban que el camino sigue abierto tras una obra. Sin mantenimiento, cada cambio obliga a explorar de nuevo.

Un ciclo de mantenimiento responsable

  1. Comprender: leer contrato, código, ejemplos y pruebas antes de modificar.
  2. Reproducir: conservar la entrada y el resultado que muestran el problema.
  3. Proteger: añadir o identificar una prueba que fallaría si el defecto reapareciese.
  4. Cambiar: aplicar la modificación más pequeña que responda a la causa.
  5. Revisar: actualizar nombres o documentación que hayan quedado inexactos.
  6. Comprobar: ejecutar todas las pruebas relevantes, incluidas las antiguas.
Código y documentación deben coincidir. Un comentario desactualizado puede ser peor que su ausencia. Cuando cambia el contrato de una función, deben revisarse su docstring, sus llamadas, sus casos límite y sus pruebas.

Glosario del tema

Fallo
Comportamiento observable que no coincide con el resultado esperado.
Error de sintaxis
Incumplimiento de la gramática de Python que impide iniciar la ejecución del código.
Excepción
Objeto que representa una situación anómala detectada durante la ejecución y que puede propagarse o gestionarse.
Error lógico
Defecto por el que el programa se ejecuta, pero produce una decisión o un resultado incorrecto.
Traza
Relación de marcos de llamada que muestra el recorrido de ejecución hasta una excepción.
Depuración
Proceso sistemático de reproducir un fallo, localizar su causa, corregirla y verificar el resultado.
Punto de interrupción
Marca que detiene la ejecución en un lugar elegido para inspeccionar el estado.
Contrato
Descripción de las entradas admitidas, el resultado y las condiciones que una función promete cumplir.
Caso límite
Entrada situada en un extremo o cerca de una frontera donde cambia el comportamiento.
Aserción
Comprobación que provoca AssertionError cuando una condición esperada es falsa.
Refactorización
Mejora de la estructura interna del código sin cambiar su comportamiento observable.
Regresión
Reaparición de un defecto o pérdida de un comportamiento correcto tras una modificación.
Docstring
Cadena situada al comienzo de un módulo, clase o función para documentar su uso y propósito.
Mantenimiento
Trabajo de comprender, corregir, adaptar y comprobar un programa a lo largo del tiempo.

Resumen esencial

  1. Los errores de sintaxis impiden ejecutar; las excepciones aparecen durante la ejecución; los errores lógicos producen resultados incorrectos sin detener necesariamente el programa.
  2. Una traza se interpreta desde el tipo y mensaje final hacia los marcos de llamada, sin confundir el lugar de detección con la causa.
  3. Depurar exige reproducir el fallo, detenerse cerca de él, inspeccionar variables, avanzar paso a paso y contrastar una hipótesis.
  4. try, except, else y finally tienen responsabilidades distintas; conviene capturar excepciones concretas.
  5. Los casos normales muestran el uso habitual; los casos límite examinan fronteras; las entradas no válidas comprueban el rechazo definido.
  6. Una prueba compara un resultado real con otro esperado; assert ayuda a expresar esa comparación, pero no sustituye la validación.
  7. Refactorizar mejora la estructura sin cambiar el comportamiento y siempre debe ir seguido de una nueva ejecución de las pruebas.
  8. Nombres claros, funciones breves, docstrings, comentarios con propósito, estilo coherente y pruebas facilitan el mantenimiento.
